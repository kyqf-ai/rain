# 0.4.2 变更说明（实测日志验证版）

基于 2026-11-08 实际运行日志（约 100 分钟会话、7988 帧零 CRC 错误、回填 301 天 7198 小时）发现并修复
两个问题。相关场景已加入 devsim 模拟器与端到端测试。

## 后端修复

1. **src/collector.c — 设备"跨日翻转"应答造成小时数据永久丢失（数据完整性缺陷）**
   实测日志中有 4 次：请求某日 23:00 的数据，设备却返回次日 00:00 的记录，程序判定"日期不符"后
   直接丢弃，该小时从此成为永久缺口（数据库中恰好缺失这 4 个 23:00，与告警一一对应）。
   修复：识别"应答恰好是所请求小时的下一小时"这一固件行为，把应答按其真实时段入库（本就要
   请求该时段，等于省一次往返），同时把被请求的小时记入跳过表，避免每次补采都重复请求；
   日志改为明确的"记录为数据缺口"措辞。其他日期错乱仍按原样拒绝。跨进程重启后的首轮全量
   扫描仍会重探一次旧缺口（自愈设计：若设备侧修复，数据可自动补回）。

2. **src/collector.c — 当前小时逐周期重复写库与日志刷屏（效率缺陷）**
   实测日志中，poll=5 s 且当前小时有雨时，同一个"provisional"行 4 分钟内被重复写入 51 次
   （数值始终 0.1 mm 未变），数据库每 5 秒一次整行 UPSERT + 分钟表整段重写。
   修复：当前小时仅在数值变化时写库/记日志（total 为分钟计数之和，不变即数据未变）；
   整点结束后的 final 定稿写入不受影响，仍保证落库。

## 工具与测试

- tools/devsim.py 新增 `--rollover "YYYY-MM-DD HH[,..]"`（模拟实测固件跨日翻转）与
  `--rain-every-hour`（每小时确定性降雨，用于实时模式测试）；
- tests/e2e.py 新增场景 2d/2e：验证翻转应答入正确时段、缺口不再重复请求、跨进程重探恰一次、
  provisional 日志无重复（小时, 数值）对、当前小时行状态正确。

# 0.4.1 变更说明（评审修复版）

本次改动包含 3 处后端修复与 1 次网页界面重构，全部测试（165 项，含端到端与 UI 冒烟）通过。

## 后端修复

1. **src/collector.c — 修复"设备无数据"快速路径不可达（核心逻辑缺陷）**
   `xact()` 中 `quiet` 原判定为 `len > 0 && 空闲 60ms`，而返回 `XE_NODATA` 的条件却要求
   `len == 0`，两者矛盾，导致设备明确回答"该小时无数据"（仅回 AA09 结束标记）时永远走不到
   快速路径，被当作超时处理。后果：每个缺数据小时要耗费 3 个失败周期才被跳过，且补采循环
   从旧到新顺序执行，当前小时排在最后，期间"今日"数据完全停止更新（默认参数下最坏可阻塞
   约 2 小时以上），托盘还会误报"设备无响应"。
   修复：`quiet` 改为纯"线路空闲 ≥60ms"判定。修复后缺数据小时一次往返即被识别并记入
   内存跳过表，日志输出 "device has no data for ..."。

2. **src/collector.c — 接收缓冲区填满的边界处理**
   线路持续输入无法解析的数据（>512 字节垃圾流）时，原代码会以 0 长度调用 serial_read：
   POSIX 下 read() 返回 0 被当作 I/O 错误引发无谓断连重连，Windows 下则空转到超时。
   修复：缓冲区满时记录告警、丢弃缓冲并立即重试。

3. **src/web.c — 单个慢客户端不再能拖死网页服务**
   `read_request()` 原先最多允许约 50 轮 × 2 秒的读取等待（约 100 秒），期间单线程 Web
   服务完全无响应。修复：为整个请求设置 5 秒总预算。
