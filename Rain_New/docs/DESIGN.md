# 雨量采集程序 方案与设计（v0.2：托盘 GUI 版）

## 1. 目标与范围

一个 Windows 小程序：**常驻后台**与雨量计通信、把每小时/每分钟雨量写入 SQLite；
窗口可最小化到右下角托盘，出问题时托盘变色并弹气泡提醒。**展示层（图表、查询统计）暂不在本版范围。**

## 2. 需要什么 / 不需要什么

| | 内容 | 理由 |
|---|---|---|
| ✅ 需要 | 采集核心：协议、串口、SQLite、补采、重连 | 工具存在的全部理由；真机抓包 + 两版原程序交叉验证过 |
| ✅ 需要 | 托盘图标，颜色表示状态（灰=连接中/已停止，绿=正常，黄=电压低或时钟偏差大，红=故障） | 无人值守设备，一眼看出是否正常 |
| ✅ 需要 | 异常/恢复气泡提醒（只在状态**变化**时弹一次，电池低压 6 小时内不重复） | 不盯屏幕也能知道；避免刷屏 |
| ✅ 需要 | 状态窗口：状态、机号/串口、最近通信、今日雨量、电压、时钟偏差、运行统计、日志 | 现场排查必需的最小信息；全是只读 |
| ✅ 需要 | 最小化/关闭按钮都只是隐藏到托盘；只有"退出"菜单才真正退出（带确认） | 防止误点 X 导致停止采集 |
| ✅ 需要 | 单实例（再启动只会唤出已有窗口）、开机自启（托盘菜单勾选）、注销/关机时干净退出 | 串口只能被一个程序占用；断电重启后自动恢复 |
| ✅ 需要 | 采集线程"心跳"：超过 3 个周期 + 30 秒无动静，托盘变红并提醒 | 能发现程序假死，而不只是设备掉线 |
| ✅ 需要 | 首次运行自动生成 `rain.ini`；"编辑配置"用记事本打开，"重新加载"重启采集线程 | 不让用户从零写配置 |
| ✅ 需要 | 命令行诊断（`rain.exe probe "日期 小时"`、`once`、`collect`） | 首次上线要核对 AA05 字节序，需要能看到原始帧；GUI 程序会附着到调用它的命令行窗口输出 |
| ❌ 不需要 | 内置 Web 服务器与网页 | 展示层暂缓；去掉可消除端口占用、对外暴露、多一个线程的风险。代码保留在 `src/web*.c`、`web/`，**不编进 exe** |
| ❌ 不需要 | 区间统计、CSV 导出、控制台报表 | 同上，属于展示层。数据已在 SQLite 里，将来的展示程序直接读库即可（WAL 模式，读写互不阻塞） |
| ❌ 不需要 | 窗口内参数设置对话框 | 现场很少改；用 ini + 记事本更可靠，也少一大块无法在没有 Windows 的环境里测试的界面代码 |
| ❌ 不需要 | 校时、写参数命令 | 原程序实际只发 5 条命令；校时载荷未最终确认，宁可不做也不冒险改设备时钟（目前只报告时差） |
| ❌ 不需要 | 资源文件、图标文件、安装程序 | 图标用代码现画，一个 exe 拷贝即用，不依赖 `windres` |

## 3. 架构

```
┌──────────────────────── rain.exe（单进程）────────────────────────┐
│  gui_win.c  (只有这一个文件含窗口/托盘/注册表等 Win32 调用)          │
│     │ 每秒读取快照                                                  │
│  ui_logic.c (纯逻辑：颜色、文字、气泡规则；有单元测试)               │
│     │                                                                │
│  collector.c ── 采集线程 ── serial_win.c ── 雨量计 (COM, 9600 8N1)   │
│     │                                                                │
│  store.c ── SQLite (WAL) ── rain.db                                   │
└──────────────────────────────────────────────────────────────────┘
```

- **两个线程**：界面线程 + 采集线程。采集线程不碰任何界面，界面线程不碰数据库，二者只通过
  `collector_get_status()`（加锁拷贝一份快照）和日志环形缓冲交换信息，没有跨线程的窗口调用。
- **可测试性是设计目标**：除 `gui_win.c` 与 `serial_win.c` 外全部代码是可移植 C，在 Linux 上用模拟设备做完整测试；
  界面上"显示什么、什么时候弹窗"全部放在 `ui_logic.c`，`gui_win.c` 只是把结果搬到控件上。
- 工作目录在启动时切换到 exe 所在目录，所以 `rain.ini`、`rain.db`、`logs\` 都在 exe 旁边，
  不受"开机自启时当前目录是 System32"影响。

## 4. 界面行为

- **托盘**：左键单击显示窗口；右键菜单：显示窗口 / 立即同步 / 打开日志目录 / ☑开机自动启动 / 退出。
  悬停提示形如"雨量采集 - 在线 | 今日 3.20 mm"。资源管理器重启后托盘图标自动恢复。
- **窗口**：7 行状态 + 4 个按钮（立即同步、编辑配置、重新加载配置、日志目录）+ 日志框（保留最近约 300 行）。
- **开机自启**：写入 `HKCU\...\Run`（只影响当前用户，不需要管理员权限），带 `--tray` 参数，开机后直接藏到托盘；
  首次运行（刚生成默认配置）总是显示窗口，提醒检查串口号。
- **气泡规则**：变红时弹一次警告；恢复时弹一次通知；电池低于设备自身的报警阈值时警告，6 小时内不重复。

## 5. 通信协议

```
PC → 设备   55 LEN CODE SUB [ARGS] CRC_L CRC_H       LEN = 帧总长
设备 → PC   AA TYPE DATA... CRC_L CRC_H
CRC = CRC-16/KERMIT（初值 0，多项式 0x8408），覆盖 CRC 之前所有字节（含帧头），低字节在前
```

| 命令 | 应答 | 状态 |
|---|---|---|
| `55 06 01 01` 读机号 | `AA 01` + ASCII 机号（现场 `SRY1C-2211-00001`） | ✅ 真机验证 |
| `55 06 03 01` 读时间 | `AA 03` yy mm dd hh mi ss 星期（周日=0） | ✅ 真机验证 |
| `55 06 06 01` 读状态 | `AA 06`，52 字节 | ✅ 电压字段与原数据库逐项吻合 |
| `55 0B 00 01 yy mm dd hh 01` 取某小时 | 无雨 `AA 00`(10 字节)；有雨 `AA 05`(130 字节)；然后 `AA 09 00 03 16 D0` | ✅ AA00/AA09 真机验证；⚠️ AA05 未见 |
| `55 0C 13` + 7 字节时间 校时 | — | ❌ 未实现（载荷格式未最终确认） |

状态帧 `AA 06` 字段（16 位小端，mV）：[13..14] 静态电压、[15..16] 动态电压、[17..18] 太阳能电压、
[19..20] 报警阈值、[21..22] 挂起阈值；[23] 温度（待确认）；[9..12] 标志位（含义待确认，原样保存在 `device_state.flags`）。

AA05：`AA 05 yy mm dd hh` + 60×u16（每分钟翻斗计数）+ 温度 u16 + CRC，共 130 字节。
**字节序、单位为推断**（库里是高字节在前，线上多半低字节在前），程序默认 `endian=auto`
自动判断，也可在 `rain.ini` 固定为 `le`/`be`。

其余应答类型：`AA 02`、`AA 04` 在原程序中有字符串但从未被引用，用途未知；`AA 08` 在初始化握手中出现，含义未知。

## 6. 采集流程

```
连接: 打开串口 → 读机号(与配置核对,不符则拒绝存库) → 注册设备
每个周期(默认60s):
  读状态(AA06) → 取得设备时钟、电压 → 写 device_state
  从"最后一个已定稿小时+1"补到"当前小时"（最多回溯 backfill_hours，每轮最多 max_fetch 个历史小时）
  设备回答"无数据"的历史小时只记在内存里，不重复追问
失败处理: 单次请求重试 retries 次；连续 3 个周期无应答 → offline；串口 I/O 错误 → 关闭并延时重连
```

帧接收是流式的：应答可能被分成几段到达，也可能与 `AA 09` 粘在一起；坏 CRC 的帧丢弃并重试，
定长帧先按长度校验，仅在线路空闲后才按"任意长度 + CRC"兜底，避免把半截帧误判为完整帧。


## 7. 数据与存储

### 7.1 数据模型

- `rain_hour`：每小时一行，`total`（计数，mm = total ÷ unit）、`temp10`、`final`（该小时是否已结束）。
  **有这一行 = 该小时数据已知**，没有 = 缺数据。这样"没下雨"与"没采到"可以区分。
- `rain_min`：只存**有雨的分钟**（绝大多数小时一行都没有），支持点开某小时看分钟明细。
- `device_state`（最新状态/心跳）、`device_status`（状态历史，每 10 分钟一条）、`device`。
- 时间一律是**本地墙上时间**文本 `YYYY-MM-DD HH:MM:SS`（设备和电脑都是本地时间，没有时区概念；
  文本可直接用 sqlite3 命令行读，也可按字典序排序）。

### 7.2 当前小时的处理（"实时"与"定稿"）

两条间接证据：原库最后一条 `Rain_Data`（`2026/11/06 16:00`，而 `RI_LastComm` 是 16:50:19，即该小时尚未结束）
的温度是无效值 -3276.7（即 0xFFFF）；而现场抓包中**已结束**的小时（11-07 13 点等）温度字段是有效值 0.0。
推断设备对尚未结束的小时也返回数据，只是温度无效。样本只有这一条，所以这是**假设**。
据此：

- 每个采集周期都会重新读取"当前小时"，页面上用橙色柱显示为"实时"；
- 小时结束 10 秒后再读一次并标为 `final=1`（蓝色）；
- 已定稿的行**永远不会被实时数据覆盖**（单元测试覆盖）。

> 这是推断，尚未在真机上专门验证。验证方法见 README「首次上线检查」。


## 8. 验证状态（诚实版）

**已在 Linux 沙箱里真实验证（约 165 项检查）**
- 协议层 28 项（用真机抓到的原始帧逐字节核对）；配置 11 项；界面决策逻辑 20 项；存储与统计 39 项；
- **控制路径 19 项**：用和 GUI 完全相同的方式驱动采集器——起线程、读状态快照、"立即同步"（60 秒周期下 6 秒内响应）、
  2.5 秒内停止、重启（即"重新加载"）、串口不存在、机号不符；
- **端到端 48 项**：Python 模拟设备（虚拟串口，随机延迟、应答随机拆两段、5% 坏 CRC、时钟偏 11 秒、大/小端设备）
  → 采集 → SQLite，逐小时与模拟设备比对；
- 全部测试在 AddressSanitizer + UBSan 下通过；
- **ThreadSanitizer（`tests/run_tsan.sh`）**：发现了 2 处真实的数据竞争——"停止"和"立即同步"两个跨线程标志位原先是裸 `volatile int`
  （C 里不是原子操作），已改为原子读写，修复后同一测试 0 报告。这类问题 ASan 和普通测试都查不出来；
- 实际会编进 exe 的那批源文件（无 Web）在 Linux 上链接并跑通了 `once` 与 `probe`。

**只做了类型检查，没有真正编译或运行**
- `gui_win.c`、`serial_win.c`、`platform.c` 的 Windows 分支：用按 Windows SDK 签名手写的桩头文件、
  `-fshort-wchar`、`-Wall -Wextra` 检查，**0 警告**；并做了变异测试（注入 6 类错误，6 类全部被抓到），
  说明检查有效。**但桩不是真实 SDK**，真实 MinGW 上仍可能出现个别编译错误或警告。

**完全没有验证**
- ❗ **最终 exe 没有生成**（沙箱无 Windows 编译器、无网络）；
- 没有在真实 Windows 上运行过 GUI（托盘、气泡、注册表自启、单实例、窗口布局）；
- 没有接过真实设备做完整采集，没有在高 DPI / 中文版以外的系统上看过界面。

## 10. 已知限制与待办

1. 首次上线需用 `probe` 核对 AA05 字节序（README「首次上线检查」）；程序同时会把前 3 个有雨原始帧写进日志留证；
2. 校时命令未实现；原 Access 历史库未导入；
3. 无 DPI 感知（高分屏上窗口会被系统放大，略模糊）；可执行文件没有自定义图标（图标只在运行时绘制）；
4. 日志文件不会自动清理（按天一个文件，体积很小）；
5. 展示层：直接读 `rain.db` 即可，`src/web*.c`、`web/` 是现成的一版。
